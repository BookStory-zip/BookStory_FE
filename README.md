# BookStory Frontend

BookStory 독서 서비스의 React 웹앱입니다. 모바일 중심으로 책 검색, 내 서재, 독서 기록과 공개 리뷰 탐색 경험을 제공합니다.

## 기술 방향

- **확정**: React 기반 웹앱.
- **검토 제안**: TypeScript, 반응형 UI, 공통 디자인 요소.
- Vite SPA 또는 React 기반 SSR 프레임워크는 검색 노출·공유 미리보기 요구를 정한 뒤 선택합니다.
- PWA 설치, 오프라인 사용, 푸시 알림은 각각 별도 범위로 결정합니다.

## 작업 계획

- [ ] 화면 목록과 사용자 흐름, 렌더링 방식 확정
- [ ] 프로젝트 구조, 의존성·lockfile, 환경변수 예제와 실행 안내 구성
- [ ] 색상·글꼴·간격, 버튼·책 카드·리뷰 카드 등 공통 UI 정리
- [ ] 로그인·프로필과 세션 만료 처리
- [ ] 도서 검색·상세·서재 등록 화면
- [ ] 내 서재·독서 상태·리뷰 작성·공개 범위 화면
- [ ] 공개 리뷰·서재 탐색 및 운영 관련 화면 범위 확정
- [ ] 로딩·빈 화면·오류·접근 불가 상태 구현
- [ ] API 연결, 모바일·접근성 검증, 핵심 흐름 테스트와 CI 구성

전체 MVP와 세부 화면은 아직 확정 전입니다. BE 구현 전에는 합의한 API 명세에 맞는 대체 응답으로 화면을 개발합니다.

## 책임 범위

OpenAPI 기반 타입·클라이언트 생성 방식을 검토하고 참조 명세 버전을 고정합니다. API 키나 DB 비밀값은 프론트 코드와 빌드에 포함하지 않습니다. 화면에서 버튼을 숨기는 것과 별개로 BE가 접근 권한을 검사합니다.

컨테이너 배포를 선택하면 Dockerfile과 이미지 빌드는 이 레포에 둡니다. 정적 호스팅 또는 SSR 배포 방식은 추후 결정합니다.

## 프론트엔드 CI 계획

lockfile 기반 설치 → lint → 타입 검사 → 핵심 사용자 동작 테스트 → 프로덕션 빌드.

서재 등록·리뷰 작성 등 핵심 브라우저 흐름을 검증하고, 스테이징에서는 실제 BE와 통합 검증합니다. 환경 간 동일 산출물 승격을 위해 API 상대 경로나 런타임 설정을 우선 검토합니다. 환경별 빌드가 필요하면 각각 재검증합니다.

## 현재 상태

초기 계획 문서와 PR 템플릿을 준비한 단계입니다. 화면 코드와 실행 명령은 프로젝트 초기 구성 후 추가합니다.

## 브랜치 및 PR 규칙

```text
작업 브랜치 → develop → main
```

- `main`: 운영 배포 기준 브랜치. 검증된 변경만 반영합니다.
- `develop`: 다음 배포를 위한 개발 통합 브랜치입니다.
- 작업 브랜치는 최신 `develop`에서 생성하고, 해당 작업 브랜치에 커밋·push합니다.
- 작업이 끝나면 **작업 브랜치 → develop** PR을 생성합니다. develop에 직접 push하지 않습니다.
- 배포 준비가 되면 **develop → main** PR을 생성하고 검증 후 병합합니다.
- main에도 직접 push하지 않습니다. 빈 레포의 최초 초기화 커밋만 예외로 둡니다.

브랜치 이름 예시:

- `feat/12-book-search`: 기능 추가
- `fix/18-review-visibility`: 오류 수정
- `chore/3-ci-setup`: 환경·설정 작업
- `docs/5-readme`: 문서 작업
- `refactor/24-record-service`: 구조 개선

작업 PR은 squash merge, develop에서 main으로 보내는 배포 PR은 merge commit 방식을 사용합니다. 장기 브랜치 사이의 공통 이력을 유지하기 위해 배포 PR은 squash하지 않습니다. 작업 브랜치는 병합 후 삭제하되 develop과 main은 유지합니다.

긴급 수정이 필요하면 main에서 `hotfix/<설명>` 브랜치를 만들고 main으로 PR을 보냅니다. 수정 후 **main → develop** 동기화 PR을 반드시 반영합니다.

커밋과 PR 제목은 `feat: 도서 검색 추가`, `fix: 비공개 리뷰 접근 수정`, `docs: 개발 계획 정리`처럼 작성합니다. 혼자 개발하는 동안에는 타인 승인을 필수로 강제하지 않고 자체 검토와 검사 결과를 기록합니다.

## 공통 CI/CD 정책

- **CI**: develop 또는 main 대상 PR에서 검사합니다. 두 브랜치에 병합된 뒤에도 검사합니다.
- **개발 통합**: develop 변경은 개발·스테이징 검증 대상으로 사용하며 운영 배포를 실행하지 않습니다.
- **운영 배포**: main에 병합되고 CI가 통과한 버전만 배포 후보로 사용합니다.
- **CD 도입 시**: 운영 배포는 초기에는 담당자가 검증한 버전을 선택해 수동 실행합니다. 자동 배포 여부는 배포 환경을 정한 뒤 결정합니다.
- CI 실패 시 병합·배포하지 않는 것을 운영 규칙으로 합니다. 브랜치 보호로 강제할 수 있는지는 조직 요금제와 실제 CI 체크 이름을 확인한 뒤 설정합니다.
- 앱 빌드·산출물 발행은 각 앱 레포, 환경별 버전 조합·실제 배포는 Infra 레포에서 관리합니다.
- 배포는 변경 가능한 `latest` 태그만 참조하지 않고 커밋 SHA와 이미지 digest 또는 배포 ID를 기록합니다.
- FE·BE의 main 커밋만 운영 후보가 될 수 있습니다. 해당 산출물 조합을 스테이징에서 검증하고 동일한 조합을 운영으로 승격합니다.
- API 변경은 새 필드 추가 → BE 배포 → FE 전환 → 기존 필드 제거 순서로 호환성을 유지합니다.

현재 문서는 정책과 계획입니다. CI/CD 워크플로, 브랜치 보호, 서버 배포는 아직 구성하지 않았습니다.
